# Implemented architecture

`cli.py` and `mcp_server.py` call `verifier.verify`; neither computes a verdict independently. `contracts` validates claims, `policy` checks trusted JSON and its fingerprint, and `snapshots` copies eligible source and computes deterministic path/content SHA-256. The Python adapter parses AST and emits definite syntax errors and optional stub warnings without executing candidate code. `sandbox.run_checks` launches policy-controlled argv in separate Docker containers; its trusted test harness emits one nonce-delimited JSON result on stdout after execution. There is no `/results` or other writable host evidence mount. The host supervisor captures exit status, bounded stdout/stderr, validates exactly one matching record, and hashes a canonical copy under `report_provenance=trusted_harness_stdout`. `policy.decide` evaluates mandatory results and requires `provenance=live_docker`, matching artifact/policy hashes, and trusted collection metadata. `audit` stores started/completed events with ordered hash links in SQLite; `reports` verifies a report digest against a completed event.

## Process and data flow

```text
Trusted verifier host
  ├─ policy loader ── trusted policy + acceptance directory fingerprint
  ├─ snapshotter ──── candidate source copy + artifact fingerprint
  ├─ supervisor ───── Docker argv, timeout, exit code, bounded pipes
  │       │
  │       └── read-only /workspace candidate mount
  │           read-only /opt/app/acceptance trusted-suite mount (acceptance check only)
  │           no /results, ledger, policy, or final-report mount
  │
  └─ policy evaluator ── mandatory evidence + provenance + hashes ── SQLite ledger/report

Docker container (non-root, candidate-controlled execution)
  ├─ candidate tests and candidate stdout/stderr: untrusted diagnostics
  └─ trusted harness: captures Python-level candidate streams, then emits one control record
                         on the process stdout after completion
```

The nonce is generated by the host supervisor and appears in the trusted harness process arguments, so candidate code can discover it through `sys.argv` or process inspection. It is therefore an execution correlation token, not a secret. Python `print()` output is redirected to diagnostics, while direct `os.write(1, ...)` can bypass that redirection; if it creates extra bytes or records, strict full-channel parsing fails closed. The trusted acceptance suite is mounted read-only from a path outside the candidate and is fingerprinted into the policy hash.

The sample policy at `policies/python.json` uses one Python syntax command, one candidate-repository unittest command, and one mandatory trusted acceptance check. The claim cannot change the check list. Exclusions and a manifest are recorded in reports. `INCONCLUSIVE` is returned for missing Docker, timeout, corrupt/duplicate/missing nonce record, changed workspace/policy/acceptance suite/snapshot, or missing mandatory evidence; definite syntax or test failure is `REJECTED`. `NEEDS_REVIEW` is available through policy. `CHECKING` and `UNVERIFIED` are conceptual states, not durable status transitions in this version. Candidate tests remain untrusted diagnostics; only the independently stored acceptance suite can satisfy the required acceptance check.

MCP SDK 2.1.1 provides six stdio tools: validate configured claim, request verification, status, report, recent runs and audit integrity. Its paths are supplied by the host environment, not MCP call arguments. The opt-in pre-commit hook and CI wrapper call the same CLI. A bypass-resistant deployment requires protected policy/image, a trusted verifier job, and branch protection outside this repository.
